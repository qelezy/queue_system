# Отчёт «Ожидание до приёма» (`waiting-before-appointment`): содержание и правила расчёта за период

Документ задаёт **единые определения и ожидаемое содержание** отчёта для приёмки и интерпретации результатов. Идентификатор в каталоге — `waiting-before-appointment` (см. `appsettings.json` → `Reports.Catalog`). Реализация: `WaitingBeforeAppointmentReportGenerator`, сборка таблицы — `WaitingBeforeAppointmentReportBuilder`.

---

## 1. Назначение

Отчёт характеризует **длительность ожидания пациентов до начала приёма** (в операционном смысле — до **вызова** из очереди), **типичные значения**, **разброс** и **изменение показателей в течение суток** в разрезе **календарных дней** периода (см. описание в `appsettings.json`).

Отчёт отвечает на вопросы:

- Как менялось ожидание **по дням** выбранного периода?
- Каково ожидание **по каждому часу суток** (00:00–23:00) внутри дня?
- Каковы **типичное** (среднее), **минимальное** и **максимальное** ожидание и **число завершённых ожиданий** по дню и по часу?

**Без персональных данных:** в таблице **нет** ФИО пациентов, номеров талонов и разреза по врачам — только агрегированные показатели.

Оценка строится по **полям времени** талона и этапа; справочник статусов этапа **не** используется.

---

## 2. Объект анализа и разрезы

- **Базовая единица наблюдения** — одна строка **`List_item`**, для которой одновременно выполняется:
  - талон `Appointment` попадает в период по §5;
  - задано **`time_call`** (вызов на этапе зафиксирован).
- **Ожидание до вызова** (минуты) — зависит от порядка этапа в маршруте талона (`List_item.id_appointment`). Порядок этапов: по возрастанию `time_start_servicing` (пустой start — последним), как в `RouteAndPausesReportBuilder.OrderStages`.

  | Этап в маршруте | Начало отсчёта |
  |-----------------|----------------|
  | 1‑й | `Combine(date_arrival, time_arrival)` |
  | 2‑й и далее | `Combine(date_arrival, time_end_servicing)` предыдущего этапа |
  | 2‑й+, если у предыдущего нет `time_end_servicing` | fallback: `Combine(date_arrival, time_start_servicing)` предыдущего; если и его нет — наблюдение **не включается** |

  \[
  \text{waitMin} = \text{Combine}(\text{date\_arrival}, \text{time\_call}) - \text{waitStart}
  \]

  Реализация: `CatalogReportWaitingHelper` (отчёт, сравнение категорий, дашборд).

- **Разрезы:**
  - **календарный день** — `Appointment.date_arrival`;
  - **час суток** — `Appointment.time_arrival.Hour` (**в рабочем окне**, см. §6).
- У одного талона может быть **несколько** этапов с вызовом; каждый учитывается **отдельно** в агрегатах дня и часа.

`Doctor` и прочие персональные справочники в отчёте **не** используются.

---

## 3. Источники данных (внешняя БД электронной очереди)

| Сущность | Таблица | Назначение в отчёте |
|----------|---------|----------------------|
| Этап | `List_item` | `time_call`, связь с талоном. |
| Приём (талон) | `Appointment` | `date_arrival`, `time_arrival`. |

---

## 4. Определения

### 4.1. Включение единицы наблюдения

- **`time_call`** задан; **`Combine(date_arrival, time_call)`** ∈ период (§5).
- **0 ≤ ожидание < 10080** минут (формула §2).
- Для **2‑го и последующих** этапов: если у предыдущего этапа нет ни `time_end_servicing`, ни `time_start_servicing` — наблюдение **не включается**.

### 4.2. Показатели по паре (день, час) и по дню

Для множества минут ожидания после фильтра §4.1:

- **Завершённых ожиданий** — число элементов.
- **Среднее / Минимум / Максимум, мин** — при **нуле** наблюдений в ячейке: счётчик **0**, остальные колонки **«—»**; иначе `CatalogReportShared.FormatMetric` (0 → «0», иначе до **четырёх** знаков, инвариантная культура).

### 4.3. Порядок строк

Для каждого дня **`fromDo` … `toDo`** (по возрастанию даты):

1. **Интервальные строки** — только часы, попадающие в пересечение суток с **[`periodFrom`, `periodTo`]** (см. §5). На **первом** дне периода первая подпись начинается с **времени `DateFrom`** (напр. `14:30–15:00`); на **последнем** — последняя заканчивается **временем `DateTo`** (напр. `10:00–10:15`); между ними — полные часы (`HH:00–HH:00`, для *h*=23 — `23:00–00:00`). Число строк **переменное** (не всегда 24). Агрегат в ячейке — по **`time_arrival.Hour`** = *h* интервала.
2. **«Итого за день»** — **две** строки (как в отчёте «Загрузка и простои»): подпись с **colspan 2** (`report-load-table__row--day-totals-heading`), затем строка метрик (`report-load-table__row--day-totals-end`).

---

## 5. Границы периода

- Период задаётся парой **дата и время** (`DateFrom`, `DateTo` → `periodFrom`, `periodTo` через `CatalogReportShared.ParsePeriod`).
- Единица наблюдения попадает в отчёт, если **`Combine(date_arrival, time_call)`** ∈ **[`periodFrom`, `periodTo`]** (включительно).
- **`fromDo` … `toDo`** (`DateOnly` от границ периода) — календарные дни в таблице; **подписи интервалов** на первом и последнем дне обрезаются по **`periodFrom`** / **`periodTo`** (левая и правая границы параметров).

---

## 6. Содержание отчёта (что видит пользователь)

Границы периода — в подзаголовке модалки; в таблице **не** дублируются.

**Таблица: 6 колонок.**

| # | Заголовок | Детализация | Итог за день |
|---|-----------|-------------|--------------|
| 1 | Дата | `yyyy-MM-dd`; пусто в последующих строках интервальной группы дня | пусто в строке метрик |
| 2 | Интервал | `HH:mm–HH:mm` (см. §4.3); для *h*=23 — `23:00–00:00` | **«—»** в строке метрик |
| 3 | Завершённых ожиданий | §4.2 | §4.2 |
| 4 | Среднее ожидание, мин | §4.2 | §4.2 |
| 5 | Минимум, мин | §4.2 | §4.2 |
| 6 | Максимум, мин | §4.2 | §4.2 |

**Итого за день** (после интервалов дня):

1. Подпись **«Итого за день»** — с первой колонки, **colspan 2** (дата + интервал), класс `report-load-table__row--day-totals-heading`; остальные ячейки строки пустые.
2. Строка метрик — класс `report-load-table__row--day-totals-end`; колонки 3–6 — агрегат по дню.

**Итого за период** (после всех дней, как в «Поступило и завершено»):

1. Подпись **«Итого за период»** — **colspan 2**, класс `report-load-table__row--totals-start`.
2. Строка метрик — класс `report-load-table__row--period-total`; колонка «Интервал» — **«—»**; колонки 3–6 — агрегат §4.2 по **всем** наблюдениям периода (среднее — по всем минутам ожидания, не сумма дневных средних).

**Группировка даты:** как в отчёте «Поступило и завершено» — `rowspan` в HTML/PDF для **всех** интервальных строк дня; блоки итогов за день и за период **вне** `rowspan`. В CSV — перенос даты в пустых ячейках.

**Диаграмма предпросмотра:** `kind: groupedBar` — ось X: даты периода в формате **`dd-MM-yyyy`** (при периоде **> 21 дня** на диаграмме — **календарные недели** `dd.MM–dd.MM`, таблица остаётся по дням, сноска под диаграммой); **только дни с данными**; серии — **часы рабочего времени** (`Monitoring:WorkdayStartHour`–`WorkdayEndHour`), присутствующие в таблице хотя бы в один день (метки `HH:00`); внутри дня — **компактный диапазон** от минимального до максимального часа с данными, **с нулевыми интервалами между ними**; значение: **среднее ожидание (мин)** по паре (день, час). Данные — из **полной** отфильтрованной выборки. Та же диаграмма — в **HTML/PDF** (SVG перед таблицей): **на всю ширину** контента страницы (в отличие от кольцевой диаграммы load-and-downtime, ~420pt по центру). **PDF** — книжная (portrait) ориентация A4; остальные каталожные отчёты с диаграммой — альбомная (landscape).

**Предпросмотр (JSON):** при **> 500** строк детализации — усечение в генераторе, строка-подсказка, **«Итого (по полным данным)»** с метриками по **полной** выборке периода; иначе в конце — **«Итого за период»**. Экспорт — полная таблица с **«Итого за период»** и диаграммой.

Имя файла экспорта: `waiting-before-appointment.csv`.

---

## 7. Качество данных и пустые поля

- Пустой **`time_call`** — наблюдение не входит.
- День без наблюдений — **не выводится** в таблице и на диаграмме.

---

## 8. Связь с названием в конфигурации

В `appsettings.json` указано краткое описание; данный документ **уточняет и заменяет** его для разработки и приёмки.
