# Спецификация UI страницы «Отчёты»

Используй этот документ как **единый источник требований к интерфейсу** при доработке или переработке страницы отчётов (Razor + JS, см. также [reusable-ui-components-requirements.md](reusable-ui-components-requirements.md)).

## Цель экрана

Пользователь (роль не ниже менеджера) выбирает **конкретный отчёт**, задаёт **параметры** (в типичном случае — только период), **формирует** результат, просматривает **предпросмотр**, при необходимости **сохраняет или выгружает** файл, может **вернуться к параметрам** и пересобрать отчёт без повторного поиска в списке.

## Принципы UX (обязательные)

1. **Один отчёт — один фокус.** Поля параметров относятся только к выбранному отчёту; не смешивать формы разных отчётов на одном экране.
2. **Не использовать классический wizard «Шаг 1 / Шаг 2»** с нумерацией для типичного сценария (период ± одно дополнительное поле): это создаёт ощущение лишних кликов. Вместо этого — **два состояния одной панели/модалки**: «параметры» ↔ «предпросмотр».
3. **Общие параметры:** у большинства отчётов параметры — **только период** (дата-время «с» / «по»). Блок периода **всегда виден** в состоянии «параметры».
4. **Дополнительные параметры:** если у отчёта есть ещё один (или редко несколько) параметр(ов), они показываются **в той же форме**, ниже периода — условный блок **«Дополнительно»** или отдельные поля без отдельного «шага мастера».
5. **После «Сформировать»:** то же окно/панель переключается на **предпросмотр** (таблица, график, PDF-вью и т.п. — по типу отчёта). Обязательно:
   - первичное действие в режиме предпросмотра: **«Сохранить» / «Скачать»** (как принято в проекте для данного формата);
   - вторичное: **«Изменить параметры»** или **«Назад»** — возврат к форме параметров **без закрытия** контекста отчёта (пользователь не теряет выбранный отчёт).
6. **Долгая генерация:** на время запроса показывать **состояние загрузки** (блокировка кнопки, индикатор), понятное сообщение при ошибке.
7. **Масштабирование списка:** при большом числе отчётов — **группировка по категориям** (как смысловые разделы), опционально **поиск/фильтр по названию**. Длинный аккордеон со всеми отчётами на одной странице без поиска — нежелателен.

## Структура страницы (целевой макет)

### Основная область (страница «Отчёты»)

- Заголовок страницы: **«Отчёты»**.
- **Список отчётов** — основной контент:
  - элементы списка: название отчёта, при необходимости краткая подсказка или тег категории;
  - категории можно показывать как **подзаголовки секций** между группами строк, либо как вторичный текст у строки;
  - клик по строке открывает **панель или модальное окно** работы с этим отчётом (см. ниже).

Не требуется дублировать на главной странице единый блок «Параметры отчёта» для всех отчётов сразу — параметры задаются **после выбора** отчёта.

### Панель / модалка одного отчёта

Под заголовком (`register-panel-head`) контент помещён в обёртку **`report-workflow-modal__content`** с внутренними отступами от краёв диалога (см. `additions.css`).

**Состояние A — Параметры**

- Заголовок: **название выбранного отчёта** (чтобы было ясно, к чему относятся поля).
- Поля: **период «С» / «По»** (календарь + время, как в текущем UI).
- При наличии у отчёта доп. параметров — показать их **под периодом** (динамически по метаданным/типу отчёта).
- Кнопка: **«Сформировать»** (primary).

**Состояние B — Предпросмотр**

- Заголовок: тот же отчёт + при необходимости кратко указать период (read-only).
- Область предпросмотра (контент от сервера).
- Действия: **скачивание / сохранение** + **«Изменить параметры»**.

Закрытие панели/модалки возвращает пользователя к списку; при повторном открытии того же отчёта разумно **подставлять последний период** из текущей сессии (если уже реализовано в коде — сохранить поведение).

## Чего избегать

- Одна общая форма параметров внизу страницы для «всех отчётов сразу», когда у отчётов разные наборы полей — путает пользователя.
- Раскрытие всех отчётов всех категорий в виде одного гигантского аккордеона без поиска.
- Исчезновение формы параметров без явного способа **вернуться и поправить период** после предпросмотра.

## Связь с текущей реализацией (ориентиры для разработки)

Точки входа в коде (актуализировать при рефакторинге):

- Страница: `Views/Reports/Index.cshtml`
- Модалка параметров и предпросмотра: `Views/Reports/_ReportWorkflowModal.cshtml`
- Скрипты страницы: `wwwroot/js/reports-index.js`

Переработка визуала и потока должна **сохранять или улучшать** описанные выше сценарии; при изменении путей — обновить раздел «Связь с реализацией» в этом файле.
